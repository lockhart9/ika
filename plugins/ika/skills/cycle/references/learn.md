# ナレッジを育てる: 実装の結果を KB に戻す

cycle の 6 の詳しい手順。書くのは「次に判断するとき・次に作るときに効くこと」だけ。変更の一覧やコードの説明は git とリポジトリに任せる。

## 何をどこに書くか

| 分かったこと | 書き先 | 例 |
|---|---|---|
| 作ったものの今の形（要件・仕様） | 要件書（`status: done`） | 実際の画面・API・制約 |
| 構成の変化 | プロダクトの README「技術」、または `kb/projects/<name>/` の資料 | 新しい依存・テーブル・外部サービス |
| 自明でない技術の事実 | `tech` のノート | ライブラリの不具合と回避策、性能の実測値、ハマった設定 |
| 方式を選んだ理由 | `tech` の決定（`decide` スキル） | 2 で `proposed` にしていたものの結果 |
| 市場・顧客について新しく分かったこと | `business` のノート | 実装中に競合の仕様を見て分かったこと |
| 残した範囲・見つけた課題・次の候補 | README「課題・次の打ち手」 | 分割して後回しにした要件、調査で見えた需要 |
| 複数のノートに共通すること | insight（[蒸留の手順](../../capture/references/distill.md)） | 「〜なら〜を選ぶ」 |

## 要件書を閉じる

```bash
ika kb cat kb/projects/<name>/specs/<slug>.md --full
ika kb edit kb/projects/<name>/specs/<slug>.md --old "status: approved" --new "status: done"
ika kb edit kb/projects/<name>/specs/<slug>.md --old "- ブランチ:" --new "- ブランチ: feature/<slug>"
```

- 「実装の記録」: ブランチ名、コミットの短いハッシュと件名、受け入れ条件ごとの確認方法（テスト名か「手動」）、要件との差分とその理由
- 本文は計画のまま残さず、作った形に直す（要件書は今の状態を表す資料。経緯は「要件との差分」に書く）
- フロントマターの `date` を今日にする

## README の「課題・次の打ち手」

次の回のテーマの入口になる。1行1件で、何をなぜやるかが分かるように書く。

- 範囲を分割して残したもの: `- 〜（[要件書](specs/<slug>.md) の範囲外にしたもの）`
- 実装中に見つけた課題・負債: 推測なら「推測」と書く
- 調査で需要が見えたが今回は作らなかったもの: 根拠のノートへリンクする

済んだ項目は消す（経緯は要件書と git に残っている）。

## 蒸留

`ika kb orphans -p <name>` で「要整理」（3件以上）が出たら insight を作る・更新する。今回のテーマに関係するノートから先に扱う。共通点が無ければ作らない。

## 確認

`ika check` を通す。`ika kb` が出したリンク切れなどの指摘は直す。
