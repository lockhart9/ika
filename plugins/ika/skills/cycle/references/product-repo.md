# 製品リポジトリに ika を持ち込まない

製品リポジトリには ika・KB への言及を書かない。同じリポジトリで ika を使う人と使わない人が開発しているので、ika・KB・要件書への言及があると、使わない人が混乱する。KB は手元だけにあり、ほかの人は開けない。

例外は ika 自身のリポジトリ（`ika project list` で `ika` の `path`）だけ。ここでは ika が主題なので、KB への言及があってよい。

KB から製品への参照（要件書の「実装の記録」にブランチ名やコミットのハッシュを書くなど）はそのまま書いてよい。書かないのは、製品から KB への参照。

## 書かない場所

- ソースコード・コメント・テスト名・テストのデータ
- ドキュメント（README・`docs/`・CHANGELOG など）
- 設定・ignore（`.gitignore`・CI・`.claude/`・`CLAUDE.md`・`AGENTS.md`）。ika の使い方や `Bash(ika:*)` の許可を足さない
- コミットメッセージ・ブランチ名・タグ
- PR・Issue の本文とコメント（頼まれて作るときも）

## 書かない語

- `ika`・`IKA_HOME`・スキル名（`ika:cycle` など）
- KB・ナレッジベース・ノート・知見・決定ログ、`kb/` で始まるパス
- 要件書・受け入れ条件・要件 ID（`R1` など）

## 書き換え方

| 書きがち | 代わりに |
|---|---|
| コミット本文に `Spec: kb/projects/<name>/specs/<slug>.md` | 変更の内容と理由を、リポジトリの慣習どおりに書く |
| コメントに「調べた内容の全体は ika のナレッジ（…）」「KB のノートを参照」 | 出典は一次情報（法令・公式ドキュメント・料金ページ）の URL だけを書く。詳しい経緯が要るなら、そのリポジトリのドキュメントに書く |
| テスト名・コメントに `R3`・「受け入れ条件 3」 | 振る舞いの言葉で書く（例: `long_lines_keep_the_first_match`） |
| 要件書の「目的」「要件」をそのまま README・PR に貼る | 製品の読者向けに、その製品の言葉で書き直す |
| ブランチ名に `spec`・`ika` | 機能の内容を表す英字（`feature/<slug>`） |
| サブエージェントに KB の内容をそのまま渡して実装させる | この資料の規則も渡す |

## 点検

コミットの前（ステージした後）と直後に実行する。ヒットしたら、ika・KB への言及か確かめる。製品が KB・Wiki・要件書を扱うものなら、正当な記述にもヒットする。言及なら直して、コミットし直す（push 前なら `git commit --amend`）。

```bash
P='(^|[^a-z0-9_])ika([^a-z0-9_]|$)|ika:[a-z-]+|IKA_HOME|kb/(projects|tech|business)/|ナレッジベース|要件書|受け入れ条件|Spec: kb'

git diff --cached -U0 | grep '^+' | grep -inE "$P"               # コミットの前: ステージした追加行
{ git log -1 --format=%B; git branch --show-current; } | grep -inE "$P"   # コミットの直後: メッセージとブランチ名
git grep -inE "$P"                                                # 作業ツリー全体（既存の痕跡）
git log --all -i -E --grep="$P" --oneline                         # 過去のコミットメッセージ
```

何も出なければよい。`KB` 単独は単位（`10 KB`）にもヒットするので語に入れていない。要件 ID（`R1` など）も同じ理由で入れていないので、テスト名とコメントは目で確かめる。

すでにコミットや push をした痕跡は、勝手に履歴を書き換えない。見つけたことと場所をユーザーに伝え、扱いを聞く。
