# 実装・テスト・コミット（cycle の 3〜5）

要件書が `approved` になってから読む。承認後は止まらずに 3 → 4 → 5 と進め、終わったら SKILL.md の 6（ナレッジを育てる）へ戻る。

製品リポジトリには ika・KB への言及を書かない（ika 自身のリポジトリを除く）。書き換え方と点検は [product-repo.md](product-repo.md)。

## 3. 実装（承認後は止まらない）

1. リポジトリの `CLAUDE.md`・`AGENTS.md`・`README.md`・`CONTRIBUTING.md` を読み、決まりに従う。これらに ika の使い方や ika への言及を足さない
2. ブランチを作る。名前はリポジトリの慣習に合わせる（`git branch -a` と `git log --oneline -20` で確かめる。`feat/` を使っていればそれ）。慣習が無ければ `feature/<slug>`（機能の内容を表す英字。`ika`・`spec` などの語を入れない）。既定のブランチの最新から切る
3. 受け入れ条件ごとに、テストと実装を書く。既存のコードの書き方・テストの置き場所に合わせる。テスト名・コメント・ドキュメントは機能の言葉で書き、要件 ID（`R1` など）・「受け入れ条件」・要件書の文・KB の語を書かない。出典を書くなら一次情報の URL だけにし、KB のノートを出典にしない
4. 途中で分かった、自明でないこと（ライブラリの癖・回避策・性能の数字・設計の選択理由）は、その場でメモしておき 6 で記録する。変更の一覧は git に残るので書かない
5. 要件書と違う形で作ることになったら、理由をメモしておく（6 で「要件との差分」に書く）
6. 実装をサブエージェントに出すときは、[product-repo.md](product-repo.md) の規則も指示に含める

## 4. テスト

1. リポジトリのテスト・型チェック・lint・ビルドのコマンドを探す（`package.json` の scripts、`Cargo.toml`、`Makefile`、`CLAUDE.md` の記載、CI の設定）
2. 全部流す。失敗したら原因を直して流し直す
3. 同じ失敗を3回直しても通らなければ、そこで止まって状況を報告する（作業はブランチに残す）
4. テストを消す・弱める・スキップして通すことはしない。既存のテストが要件と矛盾するなら、止まって聞く
5. 受け入れ条件ごとに、どのテストで確かめたかを控える（控えは 6 で要件書に書く。製品のテストやコメントには書かない）。手動の確認が要るものは、手順を控えて報告に回す

## 5. コミット

1. コミットメッセージはリポジトリの慣習（言語・形式）に合わせ、変更の内容と理由を書く。要件書・KB のパスや ika への言及は書かない
2. 意味のまとまりごとに分けてよい。生成物・秘密情報（`.env` など）を入れない
3. コミットの前（ステージした後）と直後に、[product-repo.md](product-repo.md) の点検を実行する。ヒットしたら ika・KB への言及か確かめ、言及なら直してコミットし直す
4. **push・マージ・PR 作成はしない**。ローカルの作業ブランチにコミットして終える。あとで頼まれて PR を作るときも、本文に ika・KB・要件書のパスを書かない
