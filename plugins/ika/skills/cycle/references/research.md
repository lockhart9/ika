# 調査: KB を先に引き、足りない分だけ外を調べる

cycle の 1 の詳しい手順。目的は「要件を決めるのに足りる事実」を集めることで、網羅的な市場調査ではない。

## KB から始める

```bash
ika project show <name> --readme                       # 概要・関連する決定と知見
ika kb search <語> <言い換え> --any -p <name> -l         # プロダクトに紐づくもの
ika kb search <語> <言い換え> --any -d business -l       # 他のプロダクトで調べた市場・制度
ika kb search --type insight -l                         # 横断の知見
ika data ls                                             # 競合比較・価格などのデータセット
ika data sql "select ..."                               # 既存データで答えが出るか
```

他のプロダクトのために調べた内容（制度・競合・集客の傾向）が使えることが多い。古い日付のノートは、変わりやすい事実（価格・機能の有無）だけ確かめ直す。

## 問いを絞る

3〜5個。テーマに合わせて選ぶ。

| 観点 | 問いの例 | 主な記録先 |
|---|---|---|
| 顧客・課題 | 誰が、どの場面で困っているか。今どう凌いでいるか | business ノート |
| 競合 | 同じ課題をどう解いているか。どのプランで提供しているか。口コミの不満は何か | データセット＋ business ノート |
| 価格・収益 | 有料にする余地はあるか。相場はいくらか | データセット＋ business ノート |
| 制度・規約 | 守るべき法令・ガイドライン・プラットフォームの規約 | business ノート |
| 技術の前提 | 使う API・ライブラリの制約、費用 | tech ノート |

KB で答えが出た問いは、根拠のパスを控えて調べ直さない。

## 外を調べる

- 一次情報を優先する: 公式サイト・料金ページ・ヘルプ・法令・公的機関・公式ドキュメント。まとめ記事は手がかりとして使い、事実は一次情報で確かめる
- 価格・機能・規約は変わるので、確認した日付を書く
- 確かめられなかったことは「未確認」と書く。推測で埋めない
- 1つの問いに時間をかけすぎない。要件を決めるのに足りたら止める

## 記録の形

- 1回の調査で1〜3本のノートにまとめる。問いごとに細かく分けすぎない
- 競合ごと・機能ごとの比較は、ノートの表ではなくデータセットに入れる（[capture のデータ手順](../../capture/references/data.md)）。既存のデータセットがあれば列を合わせて追記する
- ノートの冒頭「要点」に、このテーマの要件に効くことを書く（例: 「小規模向けの競合 4 社中 3 社がシフト表の CSV 出力を無料プランで提供（2026-10-21 確認）」）
