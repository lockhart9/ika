# cycle: 調査から実装まで回し、ナレッジを育てる

1回の実行で、テーマ1つ（機能1つ分）を進める。各段階の結果は KB に書き戻し、最後に書いた「次の打ち手」が次の回のテーマになる。回すほど KB が育ち、次の調査は KB にある分だけ短くなる。

KB は環境変数 `IKA_HOME` のディレクトリにある。読み書きは `ika` CLI だけで行い、KB のファイルを直接 Read/Write/rg しない。フロントマターとパスは `ika new` が作るので、書式（[references/kb-format.md](references/kb-format.md)）は `ika check` の指摘が出たときだけ読む。要件書の節は `ika new spec` のひな形（[assets/spec.md](assets/spec.md)）に沿う。

製品リポジトリには ika・KB への言及を書かない（ika 自身のリポジトリを除く）。コード・コメント・テスト名・ドキュメント・設定・コミットメッセージ・ブランチ名・PR に、ika・KB・`kb/` のパス・要件書・要件 ID を書かない。ika を使わない人も同じリポジトリで開発するため。書き換え方と点検は [references/product-repo.md](references/product-repo.md)。

進み具合は要件書（`kb/projects/<name>/specs/<slug>.md`）の `status` で表す。中断しても、要件書を見ればどこから再開するか分かる。

| status | 意味 | 次にやること |
|---|---|---|
| `draft` | 調査を終えて要件を書いた。承認待ち | 0 → 2 の承認待ち |
| `approved` | ユーザーが承認した | [references/build.md](references/build.md) を読み、3〜6 を止まらずに進める |
| `done` | 実装してコミットした | なし（次のテーマへ） |
| `dropped` | やめた | なし。理由を本文に残す |

## 0. 始める前に

1. 対象プロダクトを決める。`ika project list` で `path` を確かめ、今いるリポジトリ（`git rev-parse --show-toplevel`）と一致するか見る。リポジトリの外で頼まれたら、そのプロダクトの `path` で作業する。`path` が空のプロダクト（事業・副業の検討）は 1・2 と 6 だけ行う
2. `ika project show <name> --readme` で概要と関連を読む（長い README は「現状」「課題・次の打ち手」だけが出る。ほかの節は `ika kb cat <README> --section "技術"`）
3. テーマを決める
   - 指定があればそれ
   - 無ければ、`approved` の要件（`ika kb search --type spec --status approved -p <name> -l`）と README の「課題・次の打ち手」から候補を3つまで挙げ、ユーザーに選んでもらう。`ika kb stale -p <name>` で古くなっているもの（README がリポジトリより古い・古い価格や競合を根拠にしている決定など）が出ていれば、確かめ直しも候補にしてよい
   - 候補から選べない・テーマがまだ形になっていないときは、`brainstorm` スキルで案を広げて絞ってから戻る
   - 同じテーマの要件書がすでにあれば新しく作らず、その `status` の段階から再開する
4. 承認の前に作業ツリーを確かめる: `git status --porcelain` が空でなければ、そこで止まって扱いを聞く（他人の未コミットの変更を巻き込まない）

## 1. 調査

KB を先に引き、足りない分だけ外を調べる。詳しい進め方は [references/research.md](references/research.md)。

1. `search` スキルの手順で、テーマに関係する決定・知見・ノート・データセット・取り込んだ資料（`--type source`）を集める（`-d business` と `-d tech` の両方）。ユーザーが仕様書や資料を Drive・Notion・リポジトリに持っていると言えば、先に `import` スキルで取り込む
2. 問いを3〜5個に絞る。誰が困っているか、競合はどう解いているか（機能・価格・口コミ）、守るべき制度・規約、技術的な前提。それぞれ「KB で答えが出たか」を分ける
3. 答えが出ていない問いだけ Web で調べる。一次情報（公式サイト・料金ページ・法令・公式ドキュメント）を優先する
4. 分かったことは、その場で `capture` スキルの手順で記録する
   - 調べた事実 → `business`（技術の前提なら `tech`）のノート。出典 URL を `source:` と本文に書く
   - 競合の機能・価格のように行が増える比較 → データセット（既存があれば追記。例: `ika data ls` で探す）
   - 調査ノートは要件書の「目的」からリンクする（リンクされたノートは整理済みとして数えられる）

## 2. 要件定義（ここで1回止まる）

1. 要件書を作る（`--slug` は内容が分かる英字。ブランチ名にも使う）
   ```bash
   ika new spec "タイトル" --project <name> --tags <tag>,<tag> --slug <英字> --stdin <<'EOF'
   ...ひな形の節に沿った本文...
   EOF
   ```
   - 「目的」に根拠（1 で書いたノート・既存の知見・データセット名）をリンクする
   - 「範囲」で、やらないことを明記する。1回の実行で実装・テストし終えられる大きさに切る。大きければ分割し、残りは README の「課題・次の打ち手」に回す
   - 「要件」の受け入れ条件は、自動テストで確かめられる形で書く（「〜すると〜になる」）。テストにできないものは「手動で確認」と明記する
   - 既存の採用済みの決定（`ika kb search --type decision --status accepted -p <name>`）と矛盾しないか確かめる
   - 処理の流れ・構成・データの形・案の比較は、[references/diagrams.md](references/diagrams.md) の記法（` ```seq `・` ```flow `・` ```er ` など）で図にする
2. 選択肢があって判断が要る点（方式・範囲・価格など）は、`decide` スキルの手順で `proposed` の決定として記録し、要件書からリンクする
3. ユーザーに示して止まる。示すのは、要件書のパス、目的（一文）、範囲（やる／やらない）、受け入れ条件の一覧、未決定の点と推奨、作業ブランチ名。図つきで読めるよう `ika export html <要件書のパス>` の出力先も添える
4. 返事に合わせて進める
   - 承認 → `ika kb edit <spec> --old "status: draft" --new "status: approved"`。ユーザーが選んだ決定は `accepted` に、選ばなかった案は `rejected` にする
   - 修正の指示 → 要件書を直して、もう一度示す
   - 見送り → `status: dropped` にして、理由を本文に書く。6 の README 更新だけして終える

承認されるまで、製品リポジトリのブランチ作成・ファイル変更はしない。

## 3〜5. 実装・テスト・コミット（承認後は止まらない）

`approved` になったら [references/build.md](references/build.md) を読み、その手順で進める（承認前は読まなくてよい）。

- 3 実装: リポジトリの決まりに従い、作業ブランチで受け入れ条件ごとにテストと実装を書く
- 4 テスト: テスト・型チェック・lint・ビルドを全部流す。弱めて通さない。同じ失敗が3回続いたら止まって報告する
- 5 コミット: ローカルの作業ブランチにコミットして終える。**push・マージ・PR 作成はしない**

## 6. ナレッジを育てる

実装の結果を KB に戻す。手順の詳細は [references/learn.md](references/learn.md)。

1. 要件書を今の状態に直す: 「実装の記録」（ブランチ・コミット・受け入れ条件ごとに確かめたテスト・要件との差分）を書き、実際に作った形に本文を合わせ、`status: done` にする
2. 実装中にメモした自明でないこと（ライブラリの癖・回避策・性能の数字・設計の選択理由）を `tech` のノートにする（無ければ書かない）
3. `kb/projects/<name>/README.md` を更新する: 「現状」に日付つきで1行、「技術」の変化、「課題・次の打ち手」に分割して残した範囲・見つけた課題・調査で出た次の候補、「関連」に要件書へのリンク、フロントマターの `date` を今日に
4. `ika kb orphans -p <name>` で「要整理」が出たら、`capture` スキルの [蒸留の手順](../capture/references/distill.md) で insight を作る・更新する（承認後なので、提案で止まらず書いてよい。何を書いたかは報告に含める）
5. `ika check` を通す

## 7. 報告

最初に結果を一文で（「〜をブランチ `feature/xxx` にコミットした」）。続けて、作ったもの、受け入れ条件ごとの確認結果、手動で確かめてほしいこと、KB に書いた・直したファイルのパス、次のテーマの候補。

## しないこと

- 承認前に製品リポジトリを書き換えない
- push・マージ・PR 作成・デプロイ・本番データや外部サービスへの書き込み（メール送信・課金など）をしない。要件にそれが要るなら、そこで止まって聞く
- ユーザーが決めていないことを `accepted` の決定にしない
- テストを弱めて通さない
- KB のファイルを直接編集しない（`ika` を使う）
