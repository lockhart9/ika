# 蒸留: 未整理のノートから insight を作る

ノートは生のログで、溜めてよい。ただし溜まるだけだと検索の信頼度順が効かず、古い内容も残る。
複数のノートから言えることは **insight に書き直す**。ノートのコピー・並べ替えではなく、判断に使える一文に絞る。

## いつやるか

- ノートを書いたあと `ika kb orphans -p <name>` で「要整理」（既定は3件以上）が出たとき
- ユーザーが「整理して」「蒸留して」「まとめて」と頼んだとき

「未整理」は、どの insight・decision・プロダクトの資料（README を除く）からもリンクされていないノート。
README の「関連」は索引なので数えない。共通点がなければ、無理に作らない（ノートはそのまま残す）。

## 手順

1. `ika kb orphans -p <name>` で対象を挙げ、`ika kb cat <path>` で**全部読む**（タイトルだけで判断しない）
2. 既存の insight を探す: `ika kb fts <主題> --type insight -p <name> -l`（関連度順。当たらなければ語を外して全件を見る）。同じ主題があれば**新規ではなく更新**する（根拠の追加・知見の言い直し・反証の追記）
3. 主題を決め、ユーザーに**提案**する: 「このノート N 件から『〜』という insight を作る／〜を更新する」。ユーザーが頼んだ場合は、示したうえで進めてよい
   - 1つの insight は1つの主張。共通点が複数あれば分ける
   - 現状の設計・仕様・スキーマ・ドメインモデル（変わると古くなるもの）は insight にしない。`kb/projects/<name>/` の README か資料に書く
4. 書く（ひな形は [../assets/insight.md](../assets/insight.md)）
   ```bash
   ika new insight "タイトル" --domain <領域> --project <name> --tags a,b --slug <英字> --stdin <<'EOF'
   ## 知見
   一文で言い切る。判断に使える形（「〜なら〜を選ぶ」）。

   ## 根拠
   - [ノートのタイトル](../notes/2026/2026-10-14-foo.md): 何を示したか（一言）

   ## 当てはまらない条件・反証
   - ...

   ## 使いどころ
   どの判断のときに参照するか
   EOF
   ```
   既存の更新は `ika kb edit <path> --old ... --new ...`（根拠の追記は `ika kb append`）
5. 確認する: `ika kb orphans -p <name>` の件数が減ったこと。`ika kb` が出す指摘（リンク切れなど）を直す

## 書くときの決まり

- **根拠のノートに書いていないことは書かない。** 推測は「推測」、未確認は「未確認」と書く
- 根拠には使ったノートの相対リンクを**すべて**張る（リンクが蒸留済みの印になる）。使わなかったノートは無理に入れない
- 反証・当てはまらない条件を必ず書く。ノートから分からなければ「ノートからは不明」と書く
- ノートどうしが矛盾していたら、両方示して、どちらを採るかはユーザーに聞く
- ユーザーが決めていないことを、決定として書かない。決めたことは `decide` スキルで decision にする
- 元のノートは書き換えない・消さない。長い引用は避け、必要なら1〜2文
- 領域をまたぐときは、主に使う側の領域に置き、もう一方の関連ノートから相対リンクを張る
- 終わったら `kb/projects/<name>/README.md` の「関連」に、作った insight のリンクを足す
