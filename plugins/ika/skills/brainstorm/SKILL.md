# brainstorm: KB を踏まえて考えを広げて絞る

開発の機能・市場調査で調べること・自分のタスクについて、本人の考えを問いで広げ、どれに進むかを絞り、次のスキル（`cycle`・`decide`・`capture`）に渡す。毎回ゼロから始めず、前に見送った案・調べたこと・決めたことを KB から引いて踏まえる。

KB は環境変数 `IKA_HOME` のディレクトリにある（未設定なら設定を頼む）。読み書きは `ika` CLI だけで行い、ファイルを直接 Read/Write/rg しない。フロントマターとパスは `ika new` が作るので、書式（[references/kb-format.md](references/kb-format.md)）は `ika check` の指摘が出たとき・CLI が無いときだけ読む。
製品リポジトリには ika・KB への言及を書かない（ika 自身のリポジトリを除く。出典は一次情報の URL だけ。詳しくは [cycle の資料](../cycle/references/product-repo.md)）。
KB にアクセスできない環境（claude.ai・ChatGPT web など）では、KB を引かずにブレストし、最後に保存先のパスとフロントマター付きの本文を出力してユーザーに保存してもらう。

## 進め方の決まり

- 問いは 1 回に 1 つ。選択式（2〜4 択。ほかに自由に答えてよいと添える）を優先する。答えで中身が変わらない問いは聞かず、理由つきの提案にする
- 本人が先に出す。AI の案は、本人の案が出た後か、本人が「案を出して」と頼んだときに出す。出すときは各案の頭に【AI の案】と印を付け、一度に 3 つまでにする（AI の案を先に見せると案が似通い、自分の案という感覚が薄れる）
- 広げる間（3・4）は良し悪しを言わない。判断は 5 でまとめて行う
- KB は始めだけでなく、ブレストの間ずっと引く。添えるのは 1 件 1 行とパスまでにし、全文は本人が求めたときだけ読む。KB に無いことは「KB に記録なし」と言う
- 本人の言葉を言い換えずに残す。まとめるときも、元の言い方が分かるようにする
- 決めていないことは「案」と書く。決めること（方式・範囲・価格など）は `decide` スキルに渡し、ブレストの中で `accepted` の決定にしない

## 1. 目的と用途を決める

1. 何について考えるか、何が決まれば終わりかを一文にする（例: 「ika の次の cycle のテーマを 1 つ選ぶ」「photox の集客で調べる問いを 5 つに絞る」「今週やることを決める」）。言われていなければ、ここだけ聞く
2. 用途を決め、[references/modes.md](references/modes.md) の該当する節を読む
   - 開発（機能・設計）
   - 市場調査（調べる問いと仮説）
   - タスク整理（洗い出しと次の行動）
3. 対象のプロダクトを `ika project list` の `name` から決める。プロダクトに紐づかない個人のことなら無しでよい
4. 前回の続きかを確かめる: `ika kb search --type note -t brainstorm -p <name> -l`。続きなら、そのノートを `ika kb cat` で読み、「次の行動」から再開する

## 2. KB を引く（始める前）

本人に出してもらう前に、関係するものを集める。プロダクトがあれば:

```bash
ika project show <name> --readme                                 # 現状と「課題・次の打ち手」
ika kb search --type decision -p <name> -l                       # 決定（見送った rejected・未決の proposed を含む）
ika kb search --type spec --status approved -p <name> -l         # 承認済みでまだ作っていない要件
ika kb search --type insight -p <name> -l                        # 知見
ika kb search --type note -t brainstorm -p <name> -l             # 過去のブレスト
ika inbox ls                                                     # 受信箱（未整理のメモ）
```

テーマの語でも引く: `ika kb search <語> <言い換え> --any -l`（当たらなければ `ika kb fts <文>`）。技術とビジネスの両方（`-d tech`・`-d business`）を見る。タスク整理なら `ika kb triage` も使う（[modes.md](references/modes.md) のタスク整理の節）。

集めたものは、そのまま見せずに 10 行以内の要点にする（「前に見送った案」「まだ手を付けていない次の打ち手」「関係する知見」をそれぞれ 1 行とパスで）。

## 3. 本人が先に出す

1. 目的に向けて、思いつくことを判断せずに全部書き出してもらう。短くてよい、途中でよい、と添える
2. 出たものに番号を付けて返す。本人の言葉のまま並べ、似たものはまとめない（まとめるのは 5）
3. 出た案や話題の語で KB を引き、関係する決定・知見・ノートがあれば、その案の下に 1 行とパスで添える
   - 前に見送った案（`rejected` の決定、過去のブレストの「見送った案」）と同じものが出たら、見送った理由と、その決定の「見直す条件」を今満たしているかを添える。満たしていなければ、そう言って先に進む（却下はしない。判断は 5）
4. 本人が「浮かばない」と言ったら、4 の問いから始める。それでも出なければ、頼まれたときに限り【AI の案】を 3 つまで出す

## 4. 問いと角度を足す

1. [modes.md](references/modes.md) の問いの型から、まだ触れていない角度を 1 つずつ聞く。答えから出た新しい案は番号を足して一覧に入れる
2. 新しい語が出るたびに 3 の 3 と同じく KB を引いて添える。KB の事実（調べた価格・競合・制約）と食い違う案は、食い違いをパスつきで添える
3. 本人の案が一通り出たら、足りない角度を【AI の案】として 3 つまで出してよい。本人の案を書き換えた「改良版」は出さない（別の案として足す）
4. 止め時: 本人が出し切ったと言う／新しい案が 2 回続けて出ない／目的に足りる数が出た（開発・市場調査は 5〜15 個が目安）

## 5. まとめて選ぶ

1. 似た案をまとめ、まとめた後の一覧を出す。各案に、本人の案か【AI の案】か、元の番号を残す
2. 絞る基準を [modes.md](references/modes.md) の用途の節から示し（目的への効き・手間・不確かさなど）、各案を 1 行で評価する。比べる案が 2〜4 個なら [references/diagrams.md](references/diagrams.md) の ` ```compare ` で図にしてよい
3. 推奨を理由つきで 1 つ（タスク整理なら区分の案）示し、本人に選んでもらう（問いは 1 つ）
4. 選ばなかった案は捨てずに「見送った案」として残す。理由は本人の言葉で（「今じゃない」「手間に見合わない」など）。理由が無ければ聞く（1 問）

## 6. 記録して渡す

1. 記録する。プロダクトに紐づかない個人のタスク整理は KB に残さず、結果を会話の中で返して終える
   ```bash
   ika new note "ブレスト: <テーマ>" --domain <tech|business> --project <name> --tags brainstorm,<tag> --slug brainstorm-<英字> --stdin <<'EOF'
   ...assets/brainstorm.md の節に沿った本文...
   EOF
   ```
   - タイトルは「ブレスト: 」で始め、スラッグは `brainstorm-` で始め、タグ `brainstorm` を必ず付ける（ブレストの記録を見分ける目印。このタグはブレストの記録だけに使う）
   - 節は [assets/brainstorm.md](assets/brainstorm.md) に沿う。本人の案と【AI の案】を分け、見送った案は理由と一緒に残す
   - 領域は「何の判断に使うか」で選ぶ（どう作るか → `tech`、何を作るか・誰に届けるか・何を調べるか → `business`）
   - 前回の続きなら新しく作らず、そのノートに `ika kb append <path>` で「## <日付> の続き」を足す
2. 選んだものを渡す（渡し方は [modes.md](references/modes.md) の各節の「出口」）
   - 作る → `cycle` のテーマにする。すぐ始めないなら、本人の了承を得て README の「課題・次の打ち手」に足す（`ika kb edit`）
   - 決める → `decide` スキル（`proposed` の決定として記録する）
   - 調べる → `cycle` の調査か、`capture` スキルで調べた結果をノートにする
   - やる → 次の行動の一覧を返す。プロダクトに紐づく次の行動は、本人の了承を得て README の「課題・次の打ち手」に足す
3. 渡した先（要件書の「目的」・決定の「背景」）からブレストのノートにリンクする。渡した先が無ければ、プロダクトの README の「関連」に足す
4. `ika check` を通す。CLI が無ければ、保存先のパス（`kb/<領域>/notes/YYYY/YYYY-MM-DD-brainstorm-<英字>.md`）と、フロントマター付きの本文を出力する

## しないこと

- AI の案を本人より先に並べない（頼まれたときを除く）。本人の案を AI が書き換えない
- 一度に複数の問いを投げない。一度に 4 つ以上の AI の案を出さない
- 広げている間に案を批評・却下しない
- KB の全文を会話に貼らない
- 決めていないことを決定事項として書かない
- 個人のタスクを KB に残さない（タスク管理はしない）
